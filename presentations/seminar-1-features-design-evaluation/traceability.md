## Proposed milestones and exit evidence

- **Semester 1 demonstrator.** Build one reusable browser room with a hand-authored fixture and independently reviewed reference cases. Connect one authorized instructor PDF using bounded extraction with disclosed manual mapping where needed. Deliver the playable lab, structured definition, reference cases, test report and Stop/Continue log. Run the checks below on the bounded fixture and PDF. NAND is the illustrative first exercise within introductory digital electronics.
- **Semester 2 research prototype.** Reuse the runtime for a proposed minimum of two additional held-out PDFs spanning text-heavy and diagram-heavy inputs. Extend the allowlisted component and interaction library. Repeat acceptance per supported lab, run matched validation comparisons and pilot learning instruments if approvals and recruitment permit. Deliver a versioned corpus manifest, executable checks, paired-run evidence and a study report or protocol with recruitment status.
- **Scope.** The product vision covers educational PDFs across subjects. The study is limited to introductory digital electronics. Assume authorized legible source material, access to a domain reviewer and a supported desktop browser. Defer unrestricted inputs, physical lab substitution and multiplayer. Optional longer-term follow-on experiments must carry distinct AI-proposed or added-document provenance and pass independent verification and human review before release. They are outside the required milestones.

## Engineering acceptance

Reviewers freeze a reference manifest before seeing generated outputs. It records PDF pages, required components, steps and objectives, expected netlists, input vectors, state transitions, wrong-action behavior and known ambiguities. Use PDF annotations for source alignment and separately authored scientific fixtures for actual behavior. A circuit can follow the source and still fail an independent scientific test. Retain failures and reasons in the evidence bundle.

## Initial design and interfaces

1. **Intake.** Browser upload submits an authorized PDF. Backend creates a read-only document record with ID, SHA-256 and page anchors. Reject unsupported type or size and apply access checks before interpretation.
2. **Interpretation.** The extractor produces page-tagged evidence. The interpreter writes a versioned experiment definition. Candidate JSON fields include `documentId`, `sourceHash`, `schemaVersion`, `definitionVersion`, `objectives[]`, `components[]`, `connections[]`, `steps[]`, `expectedOutputs[]`, and `findings[]`. Objectives and steps carry IDs and page references. Connections identify component and pin pairs. Steps specify allowed actions, preconditions, expected state and feedback IDs. Findings identify provenance, affected fields and evidence.
3. **Assembly and play.** The backend binds allowed asset IDs and state transitions to the schema-valid definition. The browser renderer emits typed `actionId` and parameters and displays returned state, observations and feedback. The deterministic circuit/procedure engine owns behavior. The renderer can reuse equipment and scenes and never supplies expected scientific results.
4. **Verification and release.** Source verifier compares required content with annotated pages. Independent functional verifier runs behavior against separately authored fixtures. An instructor decision records Stop or Continue when a finding needs review. Continue can create a justified revision that rebuilds and runs both checks again. A release package contains a playable lab, evidence report, correction log and visible status. Keep the original source immutable.
5. **Technology candidates.** [Issue #11](https://github.com/Seiframy/LearnAI/issues/11) proposes comparing MarkItDown and Docling. [Three.js is a documented renderer candidate](../../New%20Unchecked%20Technologies/Added%20Value/mrdoob--three.js.md). The electronics engine, backend and persistence stack are design choices still to be evaluated. The extraction benchmark and the study comparing validation OFF vs ON answer different questions.

## Research measurement

**Technical hypothesis.** Study validation reduces source and functional errors. Use one generator and the same PDFs, initial candidate or matched initial settings, model, prompt, runtime and budget. A disables study-specific source and scientific validation. B enables both and routes findings to review. Intake, privacy, schema and allowlisted execution controls apply to both. Independently score both arms with the same frozen references, blinded to condition where feasible. Measure source coverage, unsupported claims, functional case pass rate, seeded fault detection and false alarms, end-to-end completion, latency, resource cost and human correction effort. Report paired per-PDF differences with uncertainty, distinguish pre/post-correction and keep failed runs in denominators. Determine corpus size and repetitions before a confirmatory comparison. Treat small fixture runs as pilot evidence.

**Educational hypothesis.** Practice may support conceptual understanding and application. With appropriate approvals and consent, use only independently checked labs with learners. Score comparable pre/post explanation items and an unfamiliar circuit task using separate rubrics for conceptual reasoning, action choice, procedure and interpretation. Independently double-score a subset and report scorer agreement. Record exposure, baseline, missingness and attrition. A randomized or well-matched equivalent-instruction comparison would support causal inference subject to design quality. Without it, report within-group changes as exploratory. Pilot task clarity and rubric agreement before setting a confirmatory effect target. Learner performance is a research outcome and does not serve as an engineering release gate.
